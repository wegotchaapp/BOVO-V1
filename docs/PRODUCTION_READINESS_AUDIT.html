Production readiness audit

BOVO-V1 (Bovogo carpooling platform)

Repository wegotchaapp/BOVO-V1 Branch main @ 04a3e24 Audit date 2026-10-06

Scope is the code on main. Work in open PRs (#3, #5, #6) is noted where relevant but not credited, because it is not what would ship today.

NO-GO

Two findings are live security problems: a committed database password and publicly served identity documents. Fix those before any further investment discussion.

1Executive Summary

BOVO-V1 is a monorepo for Bovogo, a Texas carpooling platform: a NestJS/TypeORM backend, a React/Vite admin console, and an Expo mobile app. The backend shows sound structural instincts, including a multi-stage non-root Dockerfile, Helmet, global validation, a health endpoint and versioned migrations. Execution falls well short of production grade. A live database password is committed in plain text, uploaded identity and vehicle documents are committed and served publicly, and payment and SMS webhooks fail open. Two spec files cover roughly 190 backend source files, with no tests at all for the mobile or admin apps. Lint reports 842 errors and has been made non-blocking. Mobile CI targets a directory that does not exist, so it fails every run. main has not moved since August 18, while hardening work waits in unmerged stacked PRs. The project is not ready for high-traffic or mission-critical use.

3Critical Gaps

  1. Leaked production database credential

    backend/fix_db_temp.js embeds a Supabase Postgres URL with its password. Rotate the password now, delete the file, purge it from history (for example with git filter-repo), and turn on GitHub secret scanning and push protection. Until it is rotated, assume the database is exposed.

  2. Identity documents are public and committed

    backend/uploads/ is in git, and /uploads is served without authentication. Remove the files from the repo and its history, move storage to a private S3 bucket with short-lived signed URLs, and check whether this counts as a reportable PII exposure.

  3. Fail-open webhooks and no rate limiting on a payments and safety platform

    Make the Stripe, Checkr and Twilio handlers reject requests when secrets are missing, verify Stripe signatures on the raw body with stripe.webhooks.constructEvent, validate Twilio signatures, register ThrottlerGuard globally, and restrict CORS to the ALLOWED_ORIGINS allowlist.

  4. CI/CD gives false confidence

    Mobile CI cannot pass, lint is advisory, the deploy pipeline is blocked by the same lint that CI ignores, and test coverage is close to zero. Fix the mobile workflow paths, clear the lint backlog and make it blocking, and add integration tests for the auth, booking, payment and SOS flows before any traffic.

  5. Delivery is stuck off main

    The hardening in PR #4 was merged into a feature branch, not main, and three stacked PRs are still open. Agree on a merge plan, land the stack with review, and start using an issue tracker so defects and their resolution time are visible.

4Final Recommendation

Decision: NO-GO

The code on main is not fit for a high-traffic, mission-critical deployment. Gaps 1 and 2 are active security incidents, not backlog items, and need fixing before any further investment discussion. The architecture is reasonable and worth saving. A realistic path is a focused 4 to 8 week hardening phase: credential rotation and history cleanup, private document storage, webhook and rate-limit fixes, working CI with blocking lint and real test coverage on money and safety flows, and a merged, reviewed main. Re-audit after that phase before a Go decision.

Evidence comes from static review of the repository, GitHub PR and Actions history, and the repo's own CI notes. The test suite and linter were not run as part of this audit.
