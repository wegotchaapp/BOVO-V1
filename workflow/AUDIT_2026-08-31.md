## D. New findings — not in any prior document

### D-1 · S1 · Insurance is charged, and no policy is ever issued

The most serious finding in this audit. It is commercial and legal, not
technical.

**Verified chain:**

1. `backend/.env` → `INSURANCE_PREMIUM=15.00`.
2. `mobile-pricing.ts:107` → `insurance = round2(PRICING.INSURANCE_PREMIUM * seats)`,
   and the field is documented *"Trip insurance is default-on; the Sailor must
   actively decline it."*
3. `mobile-pricing.ts:114-116` → `subtotal = seatSubtotal + surcharge + insurance
   + luggageInsurance`, then `totalAmount = subtotal + serviceFee`. **The premium
   is inside the amount charged.**
4. `platformGross` recognises `insurance * PRICING.INSURANCE_COMMISSION` as
   Bovogo revenue.
5. `InsuranceService.activatePolicy()` exists in
   `backend/src/modules/insurance/insurance.service.ts:18`.
6. **It has zero callers.** An exhaustive grep across `backend/src`, `admin/src`
   and `mobile/artifacts/mobile` for `InsuranceService|activatePolicy|deactivatePolicy|InsuranceModule`
   returns only: the class definition, the two method definitions, the module's
   own `providers`/`exports`, and the `app.module.ts` import. **No call site
   anywhere.**
7. `MGA_API_URL` and `MGA_API_KEY` appear in **neither `backend/.env` nor
   `.env.example`**.
8. With those unset, the service's fallback returns
   `{ policy_number: 'WG-INS-<timestamp>', status: 'active', provider: 'mock' }`
   — a **fabricated policy number**.

**So:** the premium is collected on every booking by default, commission is
recognised against it, and nothing anywhere creates a policy. The only code that
could would mint a fake number if it were wired up as it currently stands.

This must not ship in any form. It is a `USER DECISION` — see
`PRODUCTION_WORKFLOW.md` P4-1 for the three acceptable resolutions.

### D-2 · S2 · "Always" location is requested; only foreground location is used

**Verified:**

- The app's **only** location API is `Location.watchPositionAsync` at
  `hooks/useLiveLocation.ts:56`. A repo-wide grep for
  `startLocationUpdatesAsync|BackgroundGeolocation|TaskManager|requestBackgroundPermissions`
  returns **nothing**.
- `app.json` → `ios.infoPlist.UIBackgroundModes` is **not set**.
- Yet the `expo-location` plugin block declares
  `locationAlwaysAndWhenInUsePermission`, and the app ships
  `NSLocationAlwaysAndWhenInUseUsageDescription`.

**Two consequences, both real:**

1. **App Store review risk.** Apple requires a requested permission to match
   actual use. Requesting Always with no background-location capability is a
   common rejection reason.
2. **Live tracking stops when the phone locks.** During a trip — or an active
   SOS — a Sailor who pockets their phone stops being tracked. For a
   trip-safety product this is a product defect, and it is the same class as the
   "safety footer claiming tracking that isn't running" bug already fixed on this
   branch.

### D-3 · S3 · The backend test suite never exits

`npm test` hangs indefinitely; it completes only with `--forceExit`. Jest reports
*"A worker process has failed to exit gracefully"* / open handles.

In CI this is a job that burns its full timeout on **every** run, and it masks
whatever handle is being leaked. `--forceExit` is a workaround, not the fix —
`--detectOpenHandles` will name the culprit.

### D-4 · S3 · `mockup-sandbox` failure is exactly two files, and self-diagnosing

The error text names both React type trees explicitly:

```
src/components/ui/calendar.tsx(132,15)  TS2322
src/components/ui/spinner.tsx(7,6)      TS2322
  …@types+react@19.1.17/node_modules/@types/react  vs  React.Ref<…>
  "Two different types with this name exist, but they are unrelated."
```

This confirms the diagnosis in `AGENT_OPERATING_AGREEMENT.md` §1.1 — two
`@types/react` trees resolving in one pnpm workspace — and shows the blast radius
is two components in a sandbox that ships to nobody. It supports **Option A**
(drop it from the release gate) over unpinning Expo SDK 54.

### D-5 · S4 · `data_deletion_requests` is an orphan table

The name appears in exactly one file — the migration that creates it
(`1746284700000-ComplianceColumnsAddition.ts`). **No entity, no service, no
controller anywhere.**

A deletion-request table that nothing writes to is a compliance liability the
moment anyone assumes it is the record of deletion requests.
